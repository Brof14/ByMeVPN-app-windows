# Windows release audit — 2026-11-15

Status: **not ready for public release**. This is a partial audit, not evidence of a working or leak-free VPN. The Android source reference was `fb8f72d11f319e1c36493d99ad403b26049210ee`; it was inspected without changing the Android worktree. The Windows checkout started at `daf0150`.

## Confirmed issues

1. **Account changes during token refresh — partially mitigated.** Protected retries now retain an in-process account generation, and credential replacement is serialized with refresh. The account snapshot, payment creation, VPN start and logout retain the same generation across their steps. A changed account is rejected rather than replaying the request with its token. Full concurrent-login, logout, cross-process and authenticated acceptance remain unverified; do not treat the unit test as proof of complete session isolation.
2. **Privilege isolation.** `src-tauri/build.rs` requests Administrator for the entire application. The separate, authenticated, least-privilege VPN service described in `PRODUCTION_RELEASE_GATE.md` is not implemented. Do not change the manifest alone: tunnel setup depends on privileges.
3. **Android parity — partially implemented.** Password-reset requests and renewal status/cancellation now use the current Android API contract. Cancellation requires an explicit user confirmation, the checked account generation, and a server response confirming cancellation and preservation of paid access. Delivery, deployed endpoint availability, payment state and complete Android parity have not been tested against the live service.
4. **Telegram ticket exposure — fixed in this change.** On HTTP 405 the Windows client previously retried the one-time login ticket in a GET URL, exposing it to URL logs. The current Android contract is POST-only; Windows now propagates the server error instead of placing the ticket in a URL. A server supporting only the old GET endpoint must be updated before Telegram login can work with this client.
5. **Connection preflight latency — reduced for a specific case.** HTTPS connectivity checks and IP providers now run concurrently, so a working provider is not delayed by a blocked one. Preflight still requires successful HTTPS traffic through Xray before system routes change. This is not a measured throughput improvement or proof that the VPN works on a real network.

## Release evidence still required

- Real Windows 10/11 tests of each offered protocol, traffic, endpoint bypass, DNS and IPv6 behavior; disconnect, process crash, sleep/resume, network change and recovery. Local synthetic Xray config acceptance is not a connection test.
- Measured connection latency, throughput and stability against the same server and protocol as the reference client; no speed or reliability claim can be made from static analysis.
- Authenticated Windows acceptance for login, trial, account switch, device limits, subscriptions and payment status with appropriate test accounts. Do not use a real payment or activate a trial as a shortcut.
- Signed installer provenance and clean install, update, uninstall and rollback; Microsoft Store package and certification requirements have not been assessed.
- Current Android screen/state and RU/EN accessibility comparison; the previous parity documents predate substantial upstream changes.

The user asked not to start a real VPN connection or alter local network settings during this audit. Release gates are detailed in `PRODUCTION_RELEASE_GATE.md`; they are not cleared by passing unit tests.
